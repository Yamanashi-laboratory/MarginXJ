# 0001. 配布方式を JavaFX + jpackage に変更し、シミュレータは同梱しない

- ステータス: 承認
- 日付: 2026-08-16
- 対象: 配布形態、GUI 技術選定、シミュレータの入手経路

## 背景

当初の配布方針は GraalVM Native Image による単一実行ファイルでした。利用者に JDK を
入れさせないことだけが目的で、UI は picocli の CLI と対話メニューのみを想定していました。

その後、要件が次のように確定しました。

- **Windows と Linux の両対応**が必須（macOS は優先度低）。
- **他研究室にも配布する。** 利用者は Java 開発者とは限らず、JDK の導入や
  `java -jar` の実行を前提にできない。
- **JoSIM 用 SPICE ネットリストを書くための専用 GUI エディタを提供する。**
- **マージン図・結果表を GUI で表示する。** 現在の Python / matplotlib 依存
  （`margin_py.cpp` 相当、移植ステップ 7）を除去する。
- **シミュレータは JoSIM を基本とし、JoSIM が検出できない場合のみ JSIM を使う。**

GUI が必須要件になったことで、配布方式とシミュレータの扱いを見直す必要が生じました。

## 判断 1: GraalVM Native Image を取りやめ、JavaFX + jpackage に切り替える

Native Image をやめ、GUI は **JavaFX 21**、配布は **jpackage** が生成する
OS ネイティブインストーラとします。

理由:

- **Native Image と JavaFX の組み合わせは実用上困難。** JavaFX は動的なクラスロードと
  リフレクションに強く依存するため、Gluon Substrate のような専用ツールチェーンを
  持ち込まない限り再現性のあるビルドにならない。研究室で保守するビルドとしては
  複雑さが見合わない。
- **現状 native-image ビルドは一度も成功していない。** 開発端末に MSVC が無いため
  ローカルでは検証できず、CI の初回実行が最初の検証になる状態が続いていた。
  検証できていない仕組みを GUI 対応の土台にはできない。
- jpackage は JDK 標準ツールで追加依存が無く、ランタイムを同梱するため
  **利用者に JDK を入れさせない**という当初の目的はそのまま達成できる。

配布物は Windows `.msi` / Linux `.deb` / portable zip の 3 形態とします。

## 判断 2: JoSIM・JSIM のいずれもインストーラに同梱しない

シミュレータ本体は同梱せず、利用者が別途導入したものを外部プロセスとして起動します。

理由:

- **JSIM は明示的なライセンス文書を伴わずに配布されており、第三者への再配布が
  許諾されているか確認できない。** 他研究室への配布を行う以上、許諾を確認できない
  バイナリを同梱することはできない。
- **研究室ごとの独自ビルド版に対応できる。** シミュレータに手を入れて使っている
  環境でも、コマンドの場所を設定するだけで MarginXJ をそのまま使える。
- **シミュレータと MarginXJ の更新サイクルを分離できる。** JoSIM の更新のたびに
  MarginXJ を再リリースする必要がない。
- **障害の切り分けが明確になる。** 「同梱版と PATH 上の版のどちらが動いたか」という
  問題が原理的に起きない。
- **両シミュレータの扱いが対称になり例外処理が不要。** 片方だけ同梱すると、
  「同梱 JoSIM を優先するか、利用者の JoSIM を優先するか」という分岐が恒久的に残る。
  どちらも外部依存に統一すれば、検出ロジックは「JoSIM を探し、無ければ JSIM を探す」
  の一本で済む。

## 結果

- 利用者は **JoSIM を自分で導入する必要がある**（[JoSIM Releases](https://github.com/JoeyDelp/JoSIM/releases)）。
  この前提は README の冒頭で明示する。JSIM は JoSIM が見つからない場合の代替であり、必須ではない。
- インストーラにはランタイムが同梱されるため、利用者に JDK は不要。
- `build.gradle.kts` から `graalvmNative` を除去し、`org.openjfx.javafxplugin` と
  jpackage を呼ぶタスクを追加した。`fatJar` と picocli による CLI は維持する。
  GUI を導入しても CLI 経路は残し、バッチ実行を可能にしておく。
- リリース CI（`.github/workflows/release.yml`）は native-image のマトリクスから
  jpackage のマトリクスに置き換えた。
- ネイティブバイナリ特有の制約（macOS の Gatekeeper 隔離、`-D` を引数先頭に置く必要）は
  解消され、README から削除した。環境変数 `MARGINX_JOSIM_COMMAND` による指定は
  引き続き有効（利用者にとって最も確実な指定方法のため残す）。
- **未検証:** 切り替え後の `./gradlew build` はまだ実行できていない（作業端末に JDK 21 が無い）。
  とくに `org.openjfx.javafxplugin` 0.1.0 と Gradle 9 の互換性は未確認。
- **未検証:** jpackage による実際のインストーラ生成はまだ行っていない。現在の
  `jpackage` タスクは雛形であり、GUI 実装（JavaFX）が入った段階で、JavaFX の
  ネイティブライブラリを含む形で起動できるか（`--module-path` や jlink ランタイムの
  要否）を改めて確認する必要がある。

## 検討した代替案

### Native Image を継続し、GUI だけ別手段で提供する

棄却。判断 1 のとおり、Native Image と JavaFX の組み合わせが実用上困難であることが
理由の中心です。GUI を別プロセス・別配布物に切り出せば理屈の上では両立しますが、
配布物が 2 つに増えて利用者の手順が煩雑になり、同梱しない方針のシミュレータと合わせて
「利用者が用意するもの」が増えすぎます。加えて、そもそも native-image ビルドが
一度も成功していないため、継続の判断を裏づける実績がありません。

### Swing で GUI を作る

棄却。JDK に同梱されており追加依存が無い点は魅力的ですが、
今回必要なのはネットリストエディタ（構文強調・編集支援）とマージン図の描画であり、
どちらも Swing では作り込みの量が大きくなります。JavaFX は CSS によるスタイリングと
チャート機能を標準で持ち、この 2 要件に直接効きます。また jpackage を使う以上、
ランタイムを同梱するため「JDK 同梱かどうか」の差は配布物のサイズにしか現れません。

### Web UI（ローカルサーバ + ブラウザ）にする

棄却。UI の開発しやすさでは有利ですが、次の理由で見送りました。

- 研究室のローカル実行ツールに HTTP サーバを常駐させるのは、ポート競合と
  セキュリティ設定（他ホストからの到達）の面で説明コストが高い。
- ローカルファイル（ネットリスト、結果 CSV）の読み書きがブラウザのサンドボックス越しになり、
  素直に書けない。本ツールはファイルを直接扱うことが主要な仕事である。
- フロントエンドのビルド系（Node.js など）が加わり、Java 単一のツールチェーンで
  完結しなくなる。保守する研究室の負担が増える。

### JoSIM のみ同梱し、JSIM は外部依存とする

棄却。JoSIM は MIT ライセンスで再配布可能なため技術的には可能で、
「インストールしてすぐ動く」という利点は大きいものです。しかし、

- 同梱版と利用者環境の版のどちらを使うかという分岐が恒久的に残り、
  判断 2 で挙げた「両者が対称であれば例外処理が不要」という利点を失う。
- 研究室ごとの独自ビルド版を使う環境では同梱版が無駄になり、
  かえって「どちらが動いているのか」を分かりにくくする。
- JoSIM の更新のたびに MarginXJ の再リリースが必要になる。

利用者の初期設定の手間は、README 冒頭での明示と、JoSIM が見つからない場合の
エラーメッセージで補うこととしました。
